# Hosting on Northflank

Use one container, a writable persistent volume at `/data`, and a stable HTTPS origin in `HEALTH_CODE_ORIGIN`. Build from the repository root with `docker build -f apps/web/Dockerfile -t health-code-web .`. The server listens on `PORT` and stores its database at `/data/inspections.sqlite` by default. `HEALTH_CODE_DATABASE` overrides the path. Use separate databases for development replay and deployment.

For hosted model calls, set `MODEL_API_KEY` in the production Doppler configuration. Set the model settings from the [CI guide](../cli/README.md#setup). Run `health-code setup` once per Runta account so the sandbox agent can use the stored key. Supply `RUNTA_TOKEN`, `GITHUB_TOKEN` and a stable deployment name in `HEALTH_CODE_DEPLOYMENT` through Doppler. The production server refuses to start without `GITHUB_TOKEN`, because it builds upgrade menus from GitHub. Create a fine-grained token limited to public repositories, read-only, with no account permissions, and use it for nothing else. A separate process per upgrade menu parses repository files with this token in memory. A leaked token exposes only its rate limit. Reserve a unique deployment name per volume and environment within the provider account. Use 1–16 lowercase ASCII letters or digits. The server marks running Inspections interrupted on startup. Before claiming queued work it retries cleanup of orphaned runtimes in that deployment namespace with backoff up to one minute. Report reads stay available.

The upgrade menu needs no Runta sandbox. The server builds it from GitHub and the npm registry in a separate process, with no admission, reservation, queue entry or challenge. Testing an upgrade uses the Runta account. One menu for a 15-workspace repository costs about 21 GitHub requests against the token’s 5,000 an hour. A complete menu is reused for one hour per repository and commit. The site reads at most 100 workspace manifests, an 8 MiB lockfile and 12 MiB of repository files. It runs four registry lookups at once and ends a build after 45 seconds.

Each build runs in its own Bun process with an empty environment. The server ends the process after 50 seconds or when it holds more than `HEALTH_CODE_MAX_MENU_MEMORY_MIB` (default 320, at most 4096). A build past the memory limit shows the reason and offers the sandbox listing. The process also asks the kernel to end it before the server if the container runs out of memory. Each running build can hold up to the memory limit, so `HEALTH_CODE_MENU_CONCURRENCY` times the limit, plus about 150 MB for the server, must fit the container.

Memory sets the registry response limit. `HEALTH_CODE_MAX_MENU_RESPONSE_MIB` (default 16, at most 48) is the largest registry response a build parses. Two measurements of one menu, for a pnpm monorepo with about 100 dependencies and a minimum release age, on 2026-11-26:

| Where | Response limit | Peak memory of the build | Time |
| --- | --- | --- | --- |
| Linux container at 0.2 vCPU, in the server’s process | 16 MiB | 218 MiB above the server | 25 s |
| Linux container at 0.2 vCPU, in the server’s process | 48 MiB | 413 MiB above the server | 30 s |
| macOS at full speed, in its own process | 16 MiB | 362 MiB | 7 s |
| macOS at full speed, in its own process | 48 MiB | 531 MiB | 7 s |

An idle build process holds about 80 MiB. At 16 MiB the menu lists `next`, `vite`, `playwright` and `@typescript-eslint/eslint-plugin` as skipped, because the registry’s records for them are 25 to 37 MiB. Keep 16 and 320 on a 512 MB container: 320 MiB for one build and about 150 MB for the server fit inside it. The largest menu measured on macOS, at 362 MiB, passes that limit and gets the sandbox listing offer. The same menu rose 218 MiB in the Linux container. On a container with at least 1 GB, set the response limit to 48 and the memory limit to 640 to list those packages. The page offers a sandbox listing under paid admission for a project past these limits or one GitHub cannot serve.

The worker admits ten new Inspections per visitor per UTC day, runs two at once, and accepts public repositories up to 100 MiB. The two-upgrade limit and $2 repair, $1 adoption and $5 Inspection ceilings apply to hosted work. The $10 daily budget includes outstanding reservations. Hosted inspections use an 8 GiB Runta sandbox. A cache hit uses the repository ID, inspected commit, installed library version and Northflank deployment commit (`NF_DEPLOYMENT_SHA`). A new deployment commit starts fresh. The upgrade limit also scopes a full-report hit. After a partial inspection, `cacheUpgrades.ts` indexes completed verdicts by repository, commit, release, dependency, workspace versions and target version. A retry checks the baseline in its own sandbox, links each reused upgrade to its original report and inspects outstanding targets under the usual quotas. Confirmed upgrade failures and completed inspections with no available upgrades are reusable. Every published report keeps its original URL. The dashboard distinguishes measured model cost, estimated runtime charges and pending reservations.

The public origin and SQLite path are platform settings. The server opens saved reports before starting the Doppler-backed worker and retries credential loading every 30 seconds. The production container can read its app configuration at startup using a read-only `health-code/prd` service token supplied as the Northflank runtime secret `HEALTH_CODE_RUNTIME_CONFIG_TOKEN`. Restart the service after rotating app credentials. Keep this credential out of build arguments.

Configure `HEALTH_CODE_VISITOR_KEY` with at least 32 random characters and supply `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY` and `HEALTH_CODE_ADMIN_PASSWORD` through the app's Doppler configuration. Restrict the paid endpoint to the public Northflank ingress. The worker trusts Northflank’s overwritten `X-Envoy-External-Address` for the daily network digest. Private network clients must have no route to that endpoint. Use DNS-only Cloudflare records and verify HTTPS, redirect behavior and ingress header replacement before opening admission.

Give `HEALTH_CODE_LIMITS_TOKEN` read-only access to a separate limits-only Doppler config. Set `HEALTH_CODE_DAILY_DEMO_LIMIT`, `HEALTH_CODE_CONCURRENCY`, `HEALTH_CODE_DAILY_COST_USD`, `HEALTH_CODE_MAX_REPO_MIB`, `HEALTH_CODE_MAX_UPGRADES`, `HEALTH_CODE_MAX_COST_USD`, `HEALTH_CODE_REPAIR_COST_USD` and `HEALTH_CODE_ADOPTION_COST_USD` there. Five optional settings in the same config limit free upgrade menus, including `HEALTH_CODE_MAX_MENU_RESPONSE_MIB` and `HEALTH_CODE_MAX_MENU_MEMORY_MIB` above. `HEALTH_CODE_DAILY_MENU_LIMIT` (default 30) limits fresh menus per visitor and per network per UTC day. `HEALTH_CODE_MENU_CONCURRENCY` (default 1, at most 8) limits the builds running at once, and eight more wait. Set it to 0 to pause fresh menus without a deploy: saved menus stay open and the page offers the sandbox listing. `HEALTH_CODE_GITHUB_QUOTA_FLOOR` (default 500) pauses fresh menus while fewer GitHub requests remain this hour, which keeps them for paid Inspections. The site checks the floor before it sends any request for a menu and counts the 110 requests each admitted build may still send. A repeat submission inside one minute reuses the saved menu without a GitHub request. Release notes lookups stop at 500 an hour. Each reads at most eight release pages, which leaves paid Inspections at least 1,000 of the token’s 5,000 hourly points. A configuration without these settings stays valid. The worker refreshes these values every minute. After three minutes without a valid snapshot, it pauses new paid work. Configure `HEALTH_CODE_MAX_DURATION_MS` in the app environment. Its default is 30 minutes.

Use `/health/live` for liveness and `/health/ready` for report-storage readiness. `/health/live` returns `{"live":true,"version":"<version>"}` with the installed `health-code` library version, so a deploy check can confirm which release is serving. Its `recovered` field indicates when startup cleanup has finished. Sign in to `/admin` over HTTPS with username `admin` and the Doppler password. **Fresh / reused upgrade menus** counts menus beside **Starts**. **Starts** counts paid work only. One row shows the share of menus that lead to an upgrade test. Share rate uses the completion date of an Inspection Report. “Viewers who started an inspection (7 days)” shows how many people started their own Inspection within seven days of first viewing someone else’s Inspection Report. Browser identity expires after 30 days and network digests expire after the UTC quota window. An IPv6 visitor counts by /64 network.

Every five minutes the worker checks deployment-owned runtimes that exceed the Inspection deadline plus a minute for cleanup. Startup reconciles the prior process before the worker resumes the durable queue.

Keep completed reports and published blobs indefinitely. Monitor free capacity and take an off-volume backup before schema migration. This Northflank project does not support scheduled volume backups on its current plan. For a consistent SQLite backup on a running service, use SQLite’s online backup or `VACUUM INTO` and copy the resulting database off the volume. To restore, stop the worker, mount a fresh volume, restore the database to the configured path and start a compatible image under the same origin. Open a saved report and verify a downloaded Patch against its URL digest. The server rejects unknown schema versions.
